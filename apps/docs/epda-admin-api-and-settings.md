# الإعدادات المركزية و API التكامل الخارجي

توثيق طبقة الإدارة المضافة: إعدادات مركزية ديناميكية (بما فيها SAML و OIDC و
LDAP)، ومفاتيح API للأنظمة الخارجية، وصفحتا الأدمن اللتان تديرانهما.

> **قاعدة حاكمة:** كل ما في هذا المستند محصور بـ **الأدمن على مستوى النظام**
> (`Roles.ADMIN` — تقنية المعلومات)، لا بأدوار مساحة العمل. مالك مساحة العمل
> (`OrganizationRoles.OWNER`) **لا يصل** إلى أيٍّ من هذه الصفحات ولا النقاط.

---

## ١. لماذا `Roles.ADMIN` لا `OrganizationRoles.OWNER`؟

سؤالان مختلفان، والخلط بينهما هو الخطأ الذي يجب تجنّبه:

| السؤال                               | الفاحص                         |
| ------------------------------------ | ------------------------------ |
| «أي إجراء يملكه داخل مساحة عمل؟»     | `userHasPermission`            |
| «هل يملك تغيير سلوك **النظام** كله؟» | `requireAdmin` (`Roles.ADMIN`) |

إعدادات المصادقة تُقرأ في **شاشة الدخول**، قبل وجود أي سياق مساحة عمل — فلا
يمكن أصلاً فحصها بدور مساحة عمل. ومفتاح API يعمل **بلا جلسة** وبلا الفحوص التي
تقيّد المستخدم المسجَّل، فإصداره قرار على مستوى النظام لا على مستوى مساحة عمل.

لهذا كل الصفحات والنقاط الجديدة تعيش تحت `admin-dashboard+/` وتُحرَس بـ
`requireAdmin`.

---

## ٢. الإخفاء والتأمين — ثلاث بوابات

الطلب في المواصفات كان «إخفاء الصفحات بالكامل بحيث لا يصل إليها ولا يراها إلا
الأدمن». نُفِّذ على ثلاث طبقات مستقلّة، كلٌّ منها كافية وحدها:

| #   | الطبقة                                           | الملف                                                  |
| --- | ------------------------------------------------ | ------------------------------------------------------ |
| ١   | `requireAdmin` في لودر التخطيط الأب              | `admin-dashboard+/_layout.tsx`                         |
| ٢   | `requireAdmin` في لودر و`action` كل صفحة على حدة | `settings.tsx` · `integrations.tsx`                    |
| ٣   | إخفاء `/admin-dashboard` من القائمة الجانبية     | `hooks/use-sidebar-nav-items.tsx` (`hidden: !isAdmin`) |

**الطبقة الثانية ليست تكراراً زائداً.** المسار الابن يُجلَب مباشرةً عند التنقّل
من طرف العميل وعبر طلبات `.data`، فوراثة بوابة الأب **لا تكفي** — البوابة يجب
أن تتكرّر حيث تُقدَّم البيانات فعلاً.

نقاط الـ API الإدارية (`/api/admin/*`) تفحص `requireAdmin` في `loader`
و`action` معاً.

## ٣. الإعدادات المركزية

### الجدول

`AppSetting` — مفتاح/قيمة، **غير مرتبط بمساحة عمل** (السبب في القسم ١).

| العمود        | الغرض                                                                         |
| ------------- | ----------------------------------------------------------------------------- |
| `key`         | مفتاح السجل (مفتاح أساسي)                                                     |
| `value`       | نص صريح، أو ظرف مشفَّر حين `isSecret`                                         |
| `isSecret`    | هل القيمة مشفَّرة؟ مخزَّن لا مشتقّ، ليبقى فكّ التشفير ممكناً لو تغيّر التصنيف |
| `category`    | `general` · `auth` · `saml` · `oidc` · `ldap`                                 |
| `updatedById` | آخر أدمن كتب المفتاح (`SetNull` عند حذف الحساب)                               |

### السجلّ (registry) هو مصدر الحقيقة لا الجدول

`app/modules/app-settings/registry.ts` يعرّف **أي الإعدادات موجودة**. صفٌّ في
الجدول بمفتاح غير مسجَّل **يُتجاهَل عند القراءة ويُرفَض عند الكتابة**.

هذا الانقلاب هو ما يجعل نقطة الكتابة آمنة للتعريض: `PUT` يتحقّق من مجموعة
مفاتيح ثابتة بدل أن يقبل ما يرسله المتصل.

**لإضافة إعداد:** أضِف مدخلاً في `registry.ts` — ولا شيء غيره. الصفحة، ونقطتا
الـ API، وحجب الأسرار، وتحقّق الأنواع كلّها مشتقّة منه.

### ترتيب الحلّ (resolution)

```
صفّ مخزَّن  ←  متغيّر البيئة (envFallback)  ←  القيمة الافتراضية في السجلّ
```

خطوة البيئة هي ما يجعل الجدول **اختيارياً**: نشرٌ لم يفتح شاشة الإعدادات قط
يظلّ يتصرّف تماماً كما يقول `.env`، وأول حفظ يستلم الأولوية من حينها. الترحيل
إضافي بالكامل ولا يغيّر سلوك قاعدة بيانات حيّة.

> **قيمة `null` تعني «مُسِح» لا «فارغ»** — وتسقط إلى نفس البدائل. مسح حقل في
> الواجهة يستعيد السلوك المضبوط، ولا ينتج نصاً فارغاً.

### تشفير الأسرار

`app/utils/crypto.server.ts` — AES-256-GCM في ظرف يحمل نسخته:

```
v1.<iv base64url>.<authTag base64url>.<ciphertext base64url>
```

- **GCM موثَّق**: العبث بصفّ في قاعدة البيانات يظهر كفشل فكّ تشفير، لا كقيمة
  مبدَّلة بصمت.
- **بادئة النسخة**: تغيير الصيغة لاحقاً لا يحتاج ترحيل بيانات.
- **`decryptSecret` يُرجع `null` ولا يرمي**: السبب الشائع هو تدوير
  `SESSION_SECRET` تحت الاشتقاق الاحتياطي، وفي تلك الحالة يجب أن تُعرض الشاشة
  بحقول فارغة ليعيد الأدمن إدخالها — لا أن تُسقَط الصفحة التي تُصلح المشكلة.

#### مفتاح التشفير

```bash
# ولّده هكذا وضعه في .env
openssl rand -hex 32
```

`APP_SECRETS_KEY` هو المصدر المقصود. إن غاب، يُشتق المفتاح من `SESSION_SECRET`
عبر scrypt.

> ⚠️ **تبعة الاحتياطي:** تدوير `SESSION_SECRET` على نشرٍ لم يضبط
> `APP_SECRETS_KEY` يجعل كل سرٍّ مخزَّن غير قابل للفكّ — تظهر الحقول فارغة
> ويُطلب إدخالها من جديد. لا شيء آخر ينكسر، لكن **اضبط `APP_SECRETS_KEY` في
> الإنتاج**.

### الحجب (redaction) — حيث يقع حدّ الأمان

مساران للقراءة، والفرق بينهما هو الحدّ الأمني للوحدة:

| الدالة                  | لِمَن                             | الأسرار                                  |
| ----------------------- | --------------------------------- | ---------------------------------------- |
| `getSettingsForAdmin()` | الشاشة و`GET /api/admin/settings` | تُحجب إلى `••••••••`                     |
| `getResolvedSettings()` | المستهلكون في الخادم فقط          | **نص صريح** — لا تُسلسِلها في حمولة لودر |

**الحجب يقع داخل `getSettingsForAdmin` لا في المسار**، فيرثه كل متصل — بما فيهم
أي متصل مستقبلي ينسى التفكير في الأمر.

#### فخّ النائب (placeholder) — والحارس ضدّه

النموذج يعيد إرسال `••••••••` لكل حقل سرّي لم يلمسه الأدمن. لولا معالجة صريحة،
لكان **أول حفظ للصفحة يستبدل كل سرّ بنصّ النائب**.

`updateSettings` يتخطّى أي قيمة سرّية تساوي النائب بدل تخزينها، وهناك اختبار
يحرس هذا تحديداً (`service.server.test.ts` → «skips a secret submitted as the
redaction placeholder»).

## ٤. مفاتيح API

### الجدول

`ApiKey` — **الرمز نفسه لا يُخزَّن إطلاقاً**.

| العمود           | الغرض                                                          |
| ---------------- | -------------------------------------------------------------- |
| `hashedKey`      | بصمة SHA-256 للرمز الكامل (فريدة ومفهرسة — المصادقة بحث واحد)  |
| `prefix`         | `epda_` + 8 محارف، تُعرض في القائمة ليتعرّف الأدمن على المفتاح |
| `scopes`         | قائمة القدرات، تُفحص في كل نقطة                                |
| `organizationId` | مساحة العمل الوحيدة التي يعمل فيها المفتاح                     |
| `createdById`    | الأدمن المُصدِر — الكتابات تُنسب إليه                          |
| `lastUsedAt`     | ختم استخدام، يُكتب مرة كل دقيقة على الأكثر                     |
| `expiresAt`      | انتهاء اختياري                                                 |
| `revokedAt`      | إبطال **ناعم** — الصف يبقى ليبقى سجل التدقيق                   |

### لماذا SHA-256 بلا ملح؟

مناسب هنا وغير مناسب لكلمة مرور: المُدخل 256 بت من `randomBytes`، فلا قاموس
يُهاجَم به ولا معنى لدفع كلفة عمل على بصمة تُحسب في **كل طلب API**. البصمة غير
المملَّحة هي ما يجعل المصادقة بحثاً مفهرساً واحداً.

### الرمز يُعرض مرة واحدة

عند الإنشاء فقط. لا «أظهر المفتاح مجدداً» ولا طريقة لإضافتها — المفتاح الضائع
**يُبطَل ويُصدَر بديله**، لا يُسترجَع.

### النطاقات (scopes)

`app/modules/api-key/scopes.ts`:

```
assets:read · assets:write
bookings:read · bookings:write
kits:read · locations:read · categories:read · team:read
```

القراءة والكتابة **نطاقان منفصلان لكل مورد**، لا نطاق واحد مع فحص طريقة HTTP.
تكاملٌ يسحب الجرد فقط يجب أن يكون **عاجزاً** عن تعديله، وهذه خاصية في
**الاعتماد** لا في دقّة من ضبطه. ولا نطاق يتضمّن آخر: `assets:write` لا يمنح
`assets:read` ولا العكس.

## ٥. API التكامل الخارجي — `/api/v1`

### المصادقة

```bash
curl https://<host>/api/v1/assets \
  -H "Authorization: Bearer epda_xxxxxxxx..."

# أو
curl https://<host>/api/v1/assets -H "x-api-key: epda_xxxxxxxx..."
```

الرمز **لا يُقرأ من سلسلة الاستعلام** إطلاقاً — عناوين URL تنتهي في سجلات
الوصول وسجلات الوسيط وتاريخ المتصفح.

### مساحة العمل من المفتاح لا من الطلب

**لا يوجد وسيط `organizationId` في أي نقطة تحت `/api/v1`.** لو وُجد، لأمكن
لمفتاح صادر لمساحة عمل A أن يقرأ B بمجرد أن يطلب ذلك بلطف. الاعتماد يحدّد
مساحة العمل، والطلب لا يستطيع.

> هذا يخالف عمداً واجهة الجوال (`requireMobileAuth`)، حيث رمز المستخدم يصل عدة
> مساحات عمل والعميل يختار واحدة.

### الظرف (envelope)

```jsonc
// نجاح — قائمة
{ "data": [...], "meta": { "page": 1, "perPage": 50, "total": 137, "totalPages": 3 } }

// نجاح — سجل واحد
{ "data": { ... } }

// فشل
{ "error": { "message": "...", "status": 403, "traceId": "..." } }
```

عقد منفصل عن ظرف الويب (`payload`/`error`) عمداً: تغييرٌ لأجل واجهة الويب يجب
ألّا يبدّل ما يستقبله تكامل خارجي كُتب مرة وتُرك سنوات.

`additionalData` **لا يُرسَل أبداً** — قد يحمل معرّفات داخلية وأشكال استعلامات.
التفاصيل تبقى في سجلات الخادم.

### النقاط

| الطريقة | المسار                 | النطاق            | ملاحظات                                               |
| ------- | ---------------------- | ----------------- | ----------------------------------------------------- |
| GET     | `/api/v1/ping`         | `assets:read`     | فحص الاعتماد ووقت الخادم                              |
| GET     | `/api/v1/assets`       | `assets:read`     | `search` · `status` · `lifecycleStage` · `categoryId` |
| POST    | `/api/v1/assets`       | `assets:write`    | يُنشأ بحالة `PENDING` دائماً                          |
| GET     | `/api/v1/assets/:id`   | `assets:read`     |                                                       |
| PATCH   | `/api/v1/assets/:id`   | `assets:write`    | `title` · `description` · `categoryId` · `valuation`  |
| GET     | `/api/v1/bookings`     | `bookings:read`   | `status` · `approvalState` · `from` · `to`            |
| GET     | `/api/v1/kits`         | `kits:read`       | `search`                                              |
| GET     | `/api/v1/locations`    | `locations:read`  | `search`                                              |
| GET     | `/api/v1/categories`   | `categories:read` | `search`                                              |
| GET     | `/api/v1/team-members` | `team:read`       | `search` — يستثني المحذوفين ناعماً                    |

الترقيم في الجميع: `?page=` و`?perPage=` (بحدّ أقصى 200، افتراضي 50).

### قيود مقصودة في سير العمل

هذه ليست ثغرات ناقصة — بل حدود مضبوطة:

1. **الأصل يُنشأ بحالة `PENDING` فقط.** تكاملٌ يحقن أصولاً مباشرة في `READY`
   كان سيتخطّى اعتماد المستودعات، وهو الضبط الذي وُجد سير الاستلام لأجله.
2. **`lifecycleStage` غير قابل للكتابة في `PATCH`.** نقل الأصل إلى `READY` قرار
   اعتماد يمرّ بـ `asset.approve`، ولا يجوز أن يقع كأثر جانبي لتعديل عنوان.
3. **الحجوزات للقراءة فقط.** الحجز باب سير الطلبات — الموظف يرفع، المستودعات
   تبتّ، المخزون يعلّق — وإدخال آلة في سلسلة موافقات مصمَّمة حول أشخاص قرار
   يحتاج مساراً مراجَعاً. `bookings:write` موجود في المفردات ولا نقطة تمنحه بعد.
4. **المراجع تُفحص ضدّ مساحة عمل المفتاح** قبل الكتابة. Prisma كان سيقبل معرّفاً
   أجنبياً وينشئ ارتباطاً عابراً للمنظمات.

### المُسلسِلات (serializers)

كل معالج يمرّر صفوف Prisma عبر دالة في
`app/modules/external-api/serializers.server.ts` بدل إرجاعها مباشرةً.

هذا الفصل هو المقصود: المخطط يتغيّر لأسباب داخلية (محاور تحلّ محلّ أعمدة، حقول
تُضاف لسير عمل جديد)، وتكاملٌ كُتب على `/api/v1/assets` قبل سنتين يجب أن يظلّ
يستقبل نفس الـ JSON.

**ما ليس في هذه الأشكال ليس جزءاً من العقد** — تحديداً: لا معرّفات مستخدمين
داخلية، ولا أسرار `Qr`، ولا أعمدة سير العمل الداخلي.

## ٦. نقاط الإدارة (`/api/admin/*`)

للضبط المكتوب بسكربت ولخط النشر. الشاشتان تستخدمان `action` الخاص بهما.

| الطريقة | المسار                | الجسم                                                      |
| ------- | --------------------- | ---------------------------------------------------------- |
| GET     | `/api/admin/settings` | —                                                          |
| PUT     | `/api/admin/settings` | `{ "settings": [{ "key": "...", "value": "..." }] }`       |
| GET     | `/api/admin/api-keys` | —                                                          |
| POST    | `/api/admin/api-keys` | `{ "name", "organizationId", "scopes": [], "expiresAt"? }` |
| DELETE  | `/api/admin/api-keys` | `{ "id": "..." }`                                          |

الجميع محروس بـ `requireAdmin` (جلسة أدمن، لا مفتاح API). `GET` على الإعدادات
يُرجع الأسرار محجوبة.

```bash
# مثال: تفعيل SAML بالسكربت
curl -X PUT https://<host>/api/admin/settings \
  -H "Content-Type: application/json" \
  -b "<session cookie>" \
  -d '{"settings":[
        {"key":"auth.method","value":"saml"},
        {"key":"saml.enabled","value":"true"},
        {"key":"saml.entryPoint","value":"https://login.microsoftonline.com/.../saml2"}
      ]}'
```

## ٧. منطق الدخول

`app/modules/auth/auth-config.server.ts` → `getAuthConfig()`.

شاشة الدخول كانت تقرأ `config.disableSSO` — قيمة مثبَّتة عند الإقلاع من `.env`.
صارت تسأل هذه الوحدة، فتغيير طريقة الدخول حفظٌ في الشاشة لا إعادة نشر.

### «مفعَّل» ≠ «مضبوط»

`showSsoEntryPoint` يصير `true` فقط حين تكون الطريقة المختارة **دليلاً** _و_
ذلك الدليل **مضبوطاً بالكامل**. نموذج نصف مملوء كان سيرسل الموظفين إلى تحويل
مكسور. الشرط نفسه يُفرض في `/sso-login` أيضاً — إخفاء الرابط وحده لا يمنع من
يكتب المسار مباشرةً.

`DISABLE_SSO="true"` في `.env` يبقى **مفتاح إيقاف على مستوى العملية**: لا إعداد
مخزَّن يستطيع إعادة تفعيل SSO فوقه.

### حارس الإقفال (lockout guard)

```
allowPasswordLogin = false  ⟹  يُمنع الموظف
                            ⟹  الأدمن على مستوى النظام يمرّ دائماً
```

بدونه، حفظُ تكاملِ دليلٍ بشهادة خاطئة أو مضيف غير قابل للوصول كان **يُقفل
النظام على الجميع، بما فيهم الحساب اللازم لتصحيح الإعداد** — حالة غير قابلة
للتعافي يبلغها إرسالُ نموذجٍ واحد.

الاستثناء يُفحص **من قاعدة البيانات** لا من النموذج المُرسَل، فلا يمكن ادّعاؤه.

ويُفحص **بعد** التحقّق من الاعتماد لا قبله: الفحص المبكّر كان سيسمح لمتصل غير
مصادَق بمعرفة أي العناوين تخصّ أدمن، بمقارنة أيّها يُرفض.

## ٨. ما يجب أن تشغّله

```bash
# 1. توليد عميل Prisma بالجدولين الجديدين
pnpm db:generate

# 2. مسح ذاكرة Vite المؤقتة — تحتفظ بنسخة مُحسَّنة مسبقاً من @prisma/client
rm -rf apps/webapp/node_modules/.vite

# 3. تطبيق الترحيل
pnpm db:deploy-migration

# 4. مفتاح تشفير الأسرار (أضِفه إلى .env)
openssl rand -hex 32

# 5. التحقق الكامل
pnpm webapp:validate
```

بعدها: ادخل بحساب `admin@epda.local` ← **Admin dashboard** ← تبويبا
**Settings** و **Integration**.

## ١٠. ما لم يُنفَّذ بعد

هذه الطبقة تضبط SAML و OIDC و LDAP وتخزّن اعتماداتها بأمان، وتقرأ منها شاشة
الدخول. لكن:

- **نقل SAML** يمرّ عبر Supabase (`utils/sso.server.ts`) — الإعدادات هنا
  تتحكّم بالعرض والاختيار، وربطها بضبط Supabase خطوة تالية.
  انظر [epda-azure-entra-sso.md](./epda-azure-entra-sso.md).
- **عميلا OIDC و LDAP غير مكتوبين.** الإعدادات جاهزة و`getAuthConfig()` هو
  المكان الوحيد الذي سيقرآن منه، فلا شيء آخر يتغيّر حين يصلان.
- **`bookings:write`** معرَّف في مفردات النطاقات ولا نقطة تمنحه (القسم ٥).
