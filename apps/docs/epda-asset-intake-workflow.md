# مسار استلام الأصول (Asset intake workflow)

قبل هذا التغيير، كل أصل يُنشأ يصبح **متاحاً فوراً** لكل الموظفين. هذا لا يطابق
سير العمل الفعلي في الهيئة: الأصل الجديد يمر على **المالية** لإتمام الترميز
المالي، ثم تأتي **المستودعات** لتعتمده وتُتيحه.

هذا المستند يشرح كيف طُبّق ذلك، وأين تُفرض القاعدة.

---

## المفهوم

حقل جديد على `Asset`:

```prisma
enum AssetLifecycleStage {
  PENDING  // قيد الانتظار — خارج التداول
  READY    // جاهز للتوزيع
}

model Asset {
  lifecycleStage AssetLifecycleStage @default(PENDING)
}
```

**مستقل تماماً عن `AssetStatus`.** الأخير مشتق من العهدة والحجوزات
(`AVAILABLE` / `IN_CUSTODY` / `CHECKED_OUT`) ويتغير تلقائياً. أما
`lifecycleStage` فقرار بشري يتخذه المستودع.

| المرحلة   | يراها الموظف العادي | قابلة للحجز | قابلة للعهدة |
| --------- | :-----------------: | :---------: | :----------: |
| `PENDING` |         ❌          |     ❌      |      ❌      |
| `READY`   |         ✅          |     ✅      |      ✅      |

الأدوار ذات الرؤية على مستوى المنشأة (المستودعات، المالية، المخزون، المشرفون)
ترى المرحلتين — قائمة `PENDING` هي قائمة عملهم.

---

## الصلاحية

إجراء جديد في `PermissionAction`:

```
approve — نقل الأصل بين مرحلتَي الاستلام
```

| الدور                | `asset.approve` |
| -------------------- | :-------------: |
| OWNER / ADMIN        |       ✅        |
| WAREHOUSE المستودعات |       ✅        |
| FINANCE المالية      |       ❌        |
| INVENTORY المخزون    |       ❌        |
| BASE / SELF_SERVICE  |       ❌        |

المالية تملك `asset.update` (تُعدّل بيانات الأصل والترميز المالي) لكنها **لا**
تملك `approve` — قرار الإتاحة للمستودعات وحدها.

---

## الانتقالات

### `PENDING → READY` — «اعتماد وإتاحة»

زر في لوحة أعلى صفحة الأصل. يُسجَّل في ملاحظات الأصل باسم من اعتمده.

### `READY → PENDING` — «إرجاع للمراجعة»

يسحب الأصل من التداول. **السبب إلزامي** — لأن هذا يُخفي أصلاً كان الموظفون
يرونه بالأمس، والملاحظة هي السجل الوحيد لسبب اختفائه.

الشرط مفروض في طبقة الخدمة (`updateAssetLifecycleStage`) لا في الواجهة، فلا
يمكن الالتفاف عليه بطلب مُركَّب يدوياً.

### الاعتماد الجماعي

في قائمة الإجراءات الجماعية بفهرس الأصول: «اعتماد» يُفرج عن كل الأصول
المحددة دفعة واحدة، ويدعم «تحديد الكل» عبر الصفحات المُفلترة
(`ALL_SELECTED_KEY`). الأصول المعتمدة مسبقاً تُتجاوَز بصمت، وتُكتب ملاحظة لكل
أصل تحرّك فعلياً.

**اتجاه الإفراج فقط.** الإرجاع يبقى فردياً: سبب واحد ملصوق على مئة أصل يجعل
سجل الملاحظات بلا قيمة.

### كيف تجد المستودعات الطابور

في الوضع المتقدم للفهرس: عمود **Intake stage** (مخفي افتراضياً — فعّله من
«إدارة الأعمدة») وفلتر بنفس الاسم يقبل `is` / `isNot` بقيمتَي المرحلة،
وافتراضه «قيد الانتظار». `PENDING` وحدها تظهر بشارة ملوّنة؛ `READY` نص عادي
لأنها الحالة الطبيعية لكل صف يراه الموظف، فلا فائدة من تلوينها.

## أين تُفرض القاعدة

**ليست إخفاءً في الواجهة.** الحجب يحدث في الاستعلام نفسه، فالعدّادات والترقيم
تبقى صحيحة ولا يوجد مسار جانبي يكشف الأصل.

### القراءة

| المسار                                | الآلية                                      |
| ------------------------------------- | ------------------------------------------- |
| فهرس الأصول (الوضع البسيط)            | `getAssets({ onlyReadyAssets })`            |
| فهرس الأصول (الوضع المتقدم — SQL خام) | `generateWhereClause(..., onlyReadyAssets)` |
| صفحة الأصل بالرابط المباشر            | `getAsset({ onlyReadyAssets })` → 404       |
| البحث السريع (Command palette)        | `getAssets({ onlyReadyAssets })`            |
| منتقي أصول الحجز (ويب + جوال)         | `getPaginatedAndFilterableAssets`           |
| منتقيات العُدد والمواقع وربط رمز QR   | `getPaginatedAndFilterableAssets`           |
| قائمة الأصول في تطبيق الجوال          | فلترة `lifecycleStage` في `where`           |
| تفاصيل الأصل في تطبيق الجوال          | `findFirst` مع فلترة المرحلة → 404          |

في كل الحالات المصدر واحد: `rolesAreScopedToOwnRecords(role)` من
`app/utils/permissions/role-scope.ts` — نفس قائمة السماح المركزية التي تحكم
بقية نطاق البيانات، فأي دور جديد يُحجب افتراضياً حتى يُسجَّل صراحةً.

### الكتابة

الحجب في القراءة وحده لا يكفي: من يعرف المعرّف يستطيع إرساله في طلب كتابة.
لذلك `assertAssetsBelongToOrg` تقبل الآن `onlyReadyAssets`، ويمرّرها مسارا
إضافة الأصول الممسوحة إلى الحجز (الويب والجوال) — بما في ذلك الأصول المستخرجة
من العُدد، حتى لا تُهرَّب وحدة غير معتمدة عبر عُدّة.

## القيم الافتراضية عند الإنشاء

| المسار                  | المرحلة                                 |
| ----------------------- | --------------------------------------- |
| نموذج إنشاء أصل         | `PENDING` افتراضياً؛ للمستودعات تغييرها |
| إنشاء دفعة من نموذج أصل | نفس اختيار النموذج أعلاه                |
| استيراد CSV             | `READY`                                 |
| نسخ أصل قائم            | `PENDING`                               |

**لماذا الاستيراد `READY`؟** الملف المستورد يصف مخزوناً موجوداً فعلياً ومُرمَّزاً
مالياً خارج النظام، و`asset.import` لا تملكه إلا أدوار تملك `approve` أصلاً —
فهو لا يمنح شيئاً لم يكن المستورِد قادراً على فعله أصلاً بأصل. إن أردتم
أن تمر المستوردات بالطابور أيضاً، فالتغيير سطر واحد في
`createAssetsFromContentImport`.

**لماذا `PENDING` عند النسخ؟** النسخة وحدة فيزيائية جديدة لم ترها المالية بعد.

الحقل في النموذج مخفي عمن لا يملك `asset.approve`، ومع ذلك يُعاد فحص الصلاحية
في الـ action: من لا يملكها ينتهي أصله عند `PENDING` مهما أرسل.

---

## الترحيل

```sql
ALTER TABLE "Asset" ADD COLUMN "lifecycleStage" ... DEFAULT 'PENDING';
UPDATE "Asset" SET "lifecycleStage" = 'READY';
```

الأصول القائمة تُرحَّل إلى `READY` عمداً: أُنشئت تحت القاعدة القديمة وكانت
ظاهرة للموظفين، وتحويلها إلى `PENDING` كان سيُخفي المخزون كله دفعةً واحدة.
تستطيع المستودعات إرجاع أي أصل منها للمراجعة فردياً.

## الاختبارات

`app/modules/asset/lifecycle-stage.test.ts` يثبّت ثلاث خصائص:

1. `approve` للمستودعات والمشرفين فقط — وليس للمالية.
2. الحقل المحذوف من النموذج ينتج `PENDING`، و`READY` المزوَّرة تُتجاهل.
3. الدور غير المسجَّل في قائمة السماح **يُحجب** عن `PENDING` — الفشل مغلق.

الخاصية الثالثة هي الأهم: لو انعكست، بدأ الموظفون يرون ويحجزون مخزوناً لم
تُفرج عنه المستودعات.

## ملاحظة جانبية: إصلاح انهيار العرض على الخادم

أثناء هذا العمل تبيّن أن `userHasPermission` كانت تعيش في وحدة `.client.ts`،
وإضافة `.client` تجعل مُلحق React Router يستبدل كل صادراتها بـ `undefined` في
حزمة **الخادم** — فأي مكوّن يُعرض على الخادم ويستدعيها يرمي
`TypeError: userHasPermission is not a function`.

كان النظام يخفي ذلك بتعطيل عرض المسارات على الخادم حتى الترطيب (hydration)،
لكن الشريط الجانبي ولوحة الأوامر تُعرض خارج تلك الشجرة، فكانت تُسقط المستند
كاملاً بخطأ 500 صامت.

الإصلاح: نقل التنفيذ إلى وحدة محايدة (`permission.validator.ts` و
`custody-and-bookings-permissions.validator.ts`)، وترحيل كل مواقع الاستدعاء
إليها، ثم **إزالة تعطيل العرض على الخادم** من `_layout.tsx`. الوحدتان
القديمتان بلاحقة `.client` بقيتا كإعادة تصدير فارغة بلا مستوردين — يمكن حذفهما.

الدرس المثبّت في تعليق داخل `_layout.tsx`: إن كسر فحصُ صلاحيةٍ عرضَ الخادم
مستقبلاً، فالإصلاح في الوحدة لا في إعادة المؤشّر الدوّار.
