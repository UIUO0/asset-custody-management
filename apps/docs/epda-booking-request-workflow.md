# مسار الطلبات (Booking request workflow)

قبل هذا التغيير، الموظف يُنشئ حجزاً ويحجزه فوراً — لا موافقة ولا مراجعة. هذا
المستند يشرح كيف صار الحجز الذي يرفعه الموظف **طلباً** يمرّ على المستودعات،
ويخضع لمراجعة المخزون.

---

## المفهوم

**الطلب هو الحجز نفسه**، وليس كياناً جديداً. أُضيف حقل موافقة على `Booking`:

```prisma
enum BookingApprovalState {
  PENDING    // بانتظار المستودعات — لا يمكن حجزه
  APPROVED   // مقبول — يتصرّف كأي حجز سابق
  REJECTED   // مرفوض مع سبب
}
```

**لماذا حقل منفصل ولا قيمة جديدة في `BookingStatus`؟** لأن `status` يُفحص
`switch` فحصاً شاملاً في عشرات المواضع، وتوسيعه كان سيغيّر كل واحد منها بصمت.
الحقلان يجيبان سؤالين مختلفين:

- `status` — أين الحجز في دورة حياته؟ (مسودة ← محجوز ← جارٍ ← منتهٍ)
- `approvalState` — هل أُذن لهذا الحجز أصلاً؟

فالحجز يمكن أن يكون `DRAFT` و `APPROVED`، أو `DRAFT` و `PENDING`.

## فصل الصلاحيات

هذا هو جوهر التصميم:

| الدور                | يقبل/يرفض | يعلّق للمراجعة |
| -------------------- | :-------: | :------------: |
| WAREHOUSE المستودعات |    ✅     |       ❌       |
| INVENTORY المخزون    |    ❌     |       ✅       |
| FINANCE المالية      |    ❌     |       ❌       |
| الموظف               |    ❌     |       ❌       |
| OWNER / ADMIN        |    ✅     |       ✅       |

الإجراءان **مستقلان تماماً** في `PermissionAction`: `approve` و `hold`.
`hold` ليس نسخة أضعف من `approve` — لو دُمجا لحصل كل دور على سلطة الآخر.
يوجد اختبار يفشل إن ملك أي دور تشغيلي الاثنين معاً.

## الانتقالات

### القبول — المستودعات

الطلب يصبح `APPROVED` ويصير الحجز قابلاً للحجز الفعلي. ملاحظة اختيارية.

### الرفض — المستودعات

`REJECTED` مع **سبب إلزامي**. الطلب **لا يُحذف**: القرار يبقى قابلاً للتدقيق،
والموظف يستطيع رؤية سبب الرفض.

### التعليق للمراجعة — المخزون

يُجمّد الطلب. وأثناء التجميد **لا تستطيع المستودعات قبوله ولا رفضه** — هذا ما
يجعل التعليق أداة رقابة لا مجرد ملاحظة. السبب إلزامي، لأن التعليق يوقف طلب
شخص آخر والسبب هو السجل الوحيد.

### فك التعليق — المخزون

يعود الطلب للطابور. ملاحظة اختيارية.

كل انتقال يُكتب في ملاحظات الحجز باسم من نفّذه.

---

## أين يُنفَّذ المنع

**عند الحجز الفعلي، لا عند إنشاء الحجز.** `reserveBooking` هي اللحظة التي
يبدأ فيها الحجز يحتجز مخزوناً، فهي اللحظة التي يجب أن تعمل فيها الموافقة:

```
if (approvalState !== APPROVED)  → 403
if (reviewHoldAt)                → 409
```

وُضع الفحص في الخدمة لا في المسارات لأن هناك عدة مداخل لنفس العملية (إجراء
صفحة الحجز في الويب، ونقطة النهاية في الجوال، وتبويب قديم مفتوح). الخدمة هي
النقطة التي تمرّ منها كلها.

الشرط نفسه مُعاد في `request.server.ts` قبل أي قرار، فالتعليق يُرفض في
الخادم لا بتعطيل الزر فقط.

---

## من يدخل الطابور

```ts
approvalState: isScopedToOwnRecords ? PENDING : APPROVED;
```

الموظف المقيّد بسجلاته يدخل طلبه الطابور. الأدوار ذات الرؤية على مستوى
المنشأة تحجز مباشرة — الطابور موجود لمراجعة ما يطلبه الموظفون، لا ليوافق
المستودع على نفسه.

**الترحيل:** كل الحجوزات القائمة صارت `APPROVED`. تركها `PENDING` كان سيُعلّق
الجدول الزمني كله بأثر رجعي، بما فيه حجوزات مصروفة فعلاً.

---

## الصفحة

`/requests` — تظهر لمن يملك `approve` أو `hold`. تعرض الطابور المعلّق فقط؛
الطلب المقرَّر يبقى في صفحة الحجز نفسه حيث سجل ملاحظاته.

الطلبات المعلّقة للمراجعة **تُرفع إلى أعلى القائمة**، ثم الأقدم فالأحدث داخل
كل مجموعة — حتى لا يتحوّل التعليق إلى نسيان دائم، ولا يتضوّر أقدم طلب في
أسفل الطابور.

في القائمة الجانبية: عنصر «الطلبات» بشارة تُظهر عدد المعلّق. العدّاد يُجلب
فقط لمن يرى الصفحة — استعلام إضافي لرقم لا يُعرض لبقية الأدوار لا معنى له.

`app/modules/booking/request.test.ts` يثبّت:

1. المستودعات تقرّر ولا تعلّق.
2. المخزون يعلّق ولا يقرّر.
3. **لا دور تشغيلي يملك الاثنين** — وهو الاختبار الذي يمنع «تبسيط» الإجراءين
   إلى واحد مستقبلاً.
4. المالية والموظفون لا يرون الصفحة أصلاً.
